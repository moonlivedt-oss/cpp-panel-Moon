### За 30 секунд

- Игра реального времени — это цикл, который крутится **много раз в секунду**: один оборот = один **кадр**.
- Время меряют `std::chrono::steady_clock` — эти часы никогда не идут назад.
- **Delta time** (`dt`) — сколько секунд прошло с прошлого кадра. Движение считают как `x += speed * dt`, тогда скорость не зависит от FPS.
- Физику и логику удобно обновлять **фиксированным шагом** (например, 50 раз в секунду) через «накопитель» времени.
- Между кадрами нужно **спать** (`sleep_until`), иначе пустой цикл съест целое ядро процессора.

```cpp
auto prev = std::chrono::steady_clock::now();
while (running) {
  auto now = std::chrono::steady_clock::now();
  double dt = std::chrono::duration<double>(now - prev).count();   // секунды с прошлого кадра
  prev = now;
  update(dt);    // x += speed * dt
  render();
}
```

## Пошаговые игры и игры реального времени

| | Пошаговая | Реального времени |
|---|---|---|
| Когда мир меняется | только после хода игрока | постоянно, даже если игрок ничего не делает |
| Цикл ждёт | ввода (`std::cin` блокирует) | не ждёт никого: кадр за кадром |
| Время | «ход» — 1 шаг | секунды: `dt` |
| Пример | шахматы, рогалик, «Подземелье» | змейка, платформер, шутер |

Всё, что было в [кирпичиках](../ref/21-igra-v-konsoli.md), — пошаговое: `readInput()` стоит и ждёт. Эта тема — о втором виде. Как читать клавиши **без ожидания** — в теме [Консоль как экран](06-konsol-ekran.md).

> **Как это в движках.** В Unreal Engine у каждого актёра есть `Tick(float DeltaTime)` — тот же самый `dt`, который ты напишешь здесь руками. Разберёшься с ним в консоли — в движке будет знакомо.

## Часы: std::chrono::steady_clock

В `<chrono>` несколько часов. Для игр и замеров нужны **`steady_clock`**: они только идут вперёд. `system_clock` — это «часы на стене»: их может перевести пользователь или синхронизация времени, и тогда у тебя получится отрицательный кадр.

```cpp
#include <chrono>
#include <iostream>
#include <thread>

int main() {
  using Clock = std::chrono::steady_clock;

  auto start = Clock::now();                                   // момент «до»
  std::this_thread::sleep_for(std::chrono::milliseconds(250)); // поспать 250 мс
  auto end = Clock::now();                                     // момент «после»

  std::chrono::duration<double> dt = end - start;              // разница в секундах, дробью
  std::cout << "прошло " << dt.count() << " с\n";              // → прошло 0.2512 с (чуть больше 0.25; на Windows бывает и 0.265)
  return 0;
}
```

Разбор:

- `Clock::now()` — «сфотографировать» текущий момент. Само число внутри не важно — важна **разница** двух моментов.
- `end - start` — длительность. `std::chrono::duration<double>` превращает её в секунды с дробной частью, `.count()` достаёт само число.
- `sleep_for` спит **не меньше** указанного — обычно чуть больше. Поэтому `0.2512`, а не ровно `0.25`. На Windows системный таймер «тикает» примерно раз в 15 мс, так что перебор до `0.265` — норма, а не поломка.

Нужны миллисекунды целым числом — так:

```cpp
auto ms = std::chrono::duration_cast<std::chrono::milliseconds>(end - start).count();   // → 250…265 (не меньше 250)
```

## Delta time: скорость в секунду, а не в кадр

Самая частая ошибка первой игры — двигать персонажа на **фиксированное число за кадр**:

```cpp
x += 5;   // ❌ 5 пикселей ЗА КАДР: при 30 FPS — 150 в секунду, при 144 FPS — 720
```

Скорость должна быть **в секунду**, а сдвиг за кадр — пропорционален прошедшему времени:

```cpp
const double speed = 200.0;   // пикселей в СЕКУНДУ
x += speed * dt;              // ✅ за секунду набежит ровно 200 при любом FPS
```

Подвигай FPS — посмотри, как меняется кадр, а скорость за секунду остаётся той же:

```live
@FPS = 60 [10..240]
---
const double speed = 240.0;       // пикселей в секунду
double dt = 1.0 / {FPS};          // секунд на кадр
x += speed * dt;                  // сдвиг за один кадр
---
Кадров в секунду: {FPS}
Длина кадра: {1000/FPS} мс
Сдвиг за кадр: {240/FPS} пикс.
За секунду: {FPS} кадров × {240/FPS} ≈ 240 пикс.
```

> Числа в живом примере целые (как `int` в C++), поэтому «≈». В настоящей игре `dt` — `double`, и за секунду выходит ровно 240.

## Фиксированный шаг обновления

`dt` каждый кадр разный: 16 мс, потом 33 мс (Windows что-то делал), потом 12 мс. Для движения это нормально, а вот для **физики и игровой логики** — неприятно: при большом `dt` быстрая пуля «перепрыгнет» стену, а результат боя будет зависеть от скорости компьютера.

Решение — обновлять логику **фиксированными порциями** времени, а лишнее копить в «накопителе»:

```cpp
const double STEP = 0.020;         // 20 мс: логика обновляется 50 раз в секунду
double acc = 0.0;                  // накопленное, но ещё не обработанное время

while (running) {
  acc += frameTime();              // сколько прошло с прошлого кадра
  while (acc >= STEP) {            // хватает на целую порцию — обновляем
    update(STEP);                  // логика всегда видит одинаковый шаг
    acc -= STEP;
  }
  render();                        // рисуем столько раз, сколько получится
}
```

Проиграй по шагам: кадры приходят неровно (50, 10, 30 мс), а логика всё равно тикает ровными порциями по 20 мс:

```steps
@id c19rm7m8
# Накопитель времени: неровные кадры → ровные шаги
acc += frameTime();
while (acc >= STEP) {
    update(STEP);
    acc -= STEP;
}
render();
---
1 | кадр=№1: 50 мс, acc (мс)=50, обновлений=0 | Первый кадр был долгим — 50 мс. Кладём их в накопитель.
2 | | 50 ≥ 20 — хватает на порцию.
3 | обновлений=1 | Логика сделала шаг ровно на 20 мс.
4 | acc (мс)=30 | Из накопителя списали 20.
?4 | обновлений=2, acc (мс)=10 | 30 ≥ 20 — ещё одна порция. Сколько останется в накопителе?
2 | | 10 < 20 — на целую порцию не хватает, остаток **ждёт** следующего кадра.
6 | | Рисуем кадр.
1 | кадр=№2: 10 мс, acc (мс)=20 | Короткий кадр: 10 + 10 = 20.
3 | обновлений=3 | Ровно одна порция.
4 | acc (мс)=0 | Накопитель пуст.
6 | | Рисуем.
1 | кадр=№3: 30 мс, acc (мс)=30 | 
3 | обновлений=4 | 
4 | acc (мс)=10 | Итог: 90 мс реального времени → 4 шага по 20 мс = 80 мс логики, 10 мс ждут в накопителе. Ничего не потерялось.
```

## Ограничение FPS: не грей процессор

Цикл без пауз крутится сотни тысяч раз в секунду и загружает ядро процессора на 100 % — вентилятор взвоет, а в консоли всё равно не видно больше 30–60 кадров. Поэтому после кадра **спят до начала следующего**:

```cpp
const auto frame = std::chrono::milliseconds(33);    // ~30 кадров в секунду
auto next = std::chrono::steady_clock::now() + frame;
while (running) {
  // ... обновить и нарисовать
  std::this_thread::sleep_until(next);   // спать ДО момента, а не «ещё 33 мс»
  next += frame;
}
```

Почему `sleep_until`, а не `sleep_for(33ms)`: кадр сам занимает время (допустим, 5 мс). С `sleep_for` получится 5 + 33 = 38 мс на кадр, и FPS «уплывёт». `sleep_until` спит ровно до нужного момента — сколько бы ни занял кадр.

## Кадр за кадром

Игровой цикл — это «прочитать ввод → обновить мир → нарисовать кадр», много раз в секунду. Посмотри на него медленно: каждый кадр символ сдвигается на `скорость × dt` клеток.

```frames
# Бегущий символ: 4 кадра в секунду
@fps 4
[@.........]
> Кадр 1: `x = 0`
---
[..@.......]
> Кадр 2: `x += speed * dt` → 2
---
[....@.....]
> Кадр 3: → 4
---
[......@...]
> Кадр 4: → 6
---
[........@.]
> Кадр 5: → 8
---
[@.........]
> Кадр 6: дошёл до края — вернулся в начало (`x = 0`)
```

## Всё вместе: бегущий символ

Настоящий цикл реального времени: символ `@` бежит по строке со скоростью 12 клеток в секунду, кадры — 10 раз в секунду, `\r` возвращает курсор в начало строки и перерисовывает её «на месте».

```cpp
#include <chrono>
#include <cstddef>
#include <iostream>
#include <string>
#include <thread>

int main() {
  using namespace std::chrono;
  const auto frame = milliseconds(100);   // 10 кадров в секунду
  const int width = 30;                   // длина дорожки
  const double speed = 12.0;              // клеток в СЕКУНДУ
  double x = 0.0;                         // позиция дробная: за кадр сдвиг ~1.2 клетки

  auto prev = steady_clock::now();
  auto next = prev + frame;
  for (int i = 0; i < 40; ++i) {          // 40 кадров ≈ 4 секунды
    auto now = steady_clock::now();
    double dt = duration<double>(now - prev).count();
    prev = now;

    x += speed * dt;                      // скорость не зависит от FPS
    while (x >= width) x -= width;        // убежал за край — появляется слева

    std::string line(static_cast<std::size_t>(width), '.');
    line[static_cast<std::size_t>(x)] = '@';
    std::cout << '\r' << line << std::flush;   // \r — в начало строки, рисуем поверх

    std::this_thread::sleep_until(next);
    next += frame;
  }
  std::cout << "\n";
  return 0;
}
```

Попробуй поменять `frame` на `milliseconds(33)` — анимация станет плавнее, а **скорость бега останется той же**. Это и есть смысл `dt`.

## Типовые ошибки

| Ошибка | Что будет | Как надо |
|---|---|---|
| `x += 5;` каждый кадр | скорость зависит от мощности компьютера | `x += speed * dt;` |
| `system_clock` для замеров | при переводе часов — отрицательный `dt`, прыжок персонажа | `steady_clock` |
| Цикл без `sleep` | 100 % одного ядра, горячий ноутбук | `sleep_until(next)` |
| `int` для позиции при `dt` | `0.7` клетки за кадр обрезаются до `0` — персонаж стоит | позиция `double`, в `int` — только при рисовании |
| Огромный `dt` после паузы (свернули окно) | персонаж пролетает сквозь стены | ограничить: `dt = std::min(dt, 0.1);` |

## Проверь себя

```quiz
В: Игра двигает героя `x += 3;` в каждом кадре. Что будет на компьютере вдвое мощнее?
+ Герой побежит примерно вдвое быстрее — кадров в секунду больше
- Ничего не изменится
- Игра не запустится
= Сдвиг «за кадр» умножается на число кадров в секунду. Скорость должна быть «в секунду»: `x += speed * dt`.

В: Какие часы брать, чтобы измерить длительность кадра?
+ `std::chrono::steady_clock`
- `std::chrono::system_clock`
- `time(nullptr)`
= `steady_clock` монотонные — никогда не идут назад. `time()` к тому же считает целыми секундами.

В: Зачем фиксированный шаг обновления, если есть `dt`?
+ Чтобы логика и физика вели себя одинаково при любом FPS и не «перепрыгивали» через препятствия
- Чтобы игра работала быстрее
- Чтобы не нужен был `sleep`
= При неровном `dt` результат расчётов зависит от длины кадра. Фиксированный шаг делает логику предсказуемой.
```

```cards
В: Что такое delta time?
О: Время (обычно в секундах), прошедшее с прошлого кадра. Движение: `x += speed * dt`.

В: Чем `sleep_until` лучше `sleep_for` в игровом цикле?
О: Спит до заданного момента, учитывая время, которое занял сам кадр, — FPS не «уплывает».

В: Что хранит накопитель в фиксированном шаге?
О: Прошедшее, но ещё не обработанное время. Пока его ≥ шага — делаем `update(STEP)` и вычитаем шаг.

Q: Зачем умножать скорость на `dt`: `x += speed * dt`?
A: Тогда движение не зависит от FPS: за секунду объект пройдёт `speed` единиц и на быстром, и на медленном компьютере.

Q: Какие часы брать для замера времени кадра?
A: `std::chrono::steady_clock` — они монотонные и не прыгают, когда меняют системное время.
H: Не `system_clock`.

Q: Как посчитать FPS?
A: Считать кадры и раз в секунду выводить счётчик и обнулять его. Для одного кадра — `1.0 / dt`.

Q: Почему физику считают фиксированным шагом, а рисуют как получится?
A: Фиксированный шаг даёт одинаковый результат при любой частоте кадров: прыжок не станет выше на мощном компьютере.
```
