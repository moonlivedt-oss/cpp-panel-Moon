## 34. Разделение на файлы

Пока программа маленькая, всё живёт в одном `.cpp` — так и надо. Но когда файл разрастается или одну и ту же функцию нужно звать из разных мест, код разносят: **объявления** в заголовок `.h`, **реализацию** в `.cpp`.

### Зачем это нужно

- **Переиспользование.** Функцию, объявленную в `.h`, может звать любой файл, который его подключит.
- **Быстрая пересборка.** Поменял одно тело в `.cpp` — пересобирается только этот `.cpp`, а не вся программа.
- **Порядок.** Заголовок — это «оглавление модуля»: видно, что он умеет, не читая реализацию.

### Кто что содержит: `.h` против `.cpp`

Разделение идёт по границе «что» и «как»:

- **`.h` (заголовок)** — то, что нужно **знать** вызывающему: прототипы функций, определения `struct`/`class`, константы. **Обещания.**
- **`.cpp` (реализация)** — тела функций. **Как именно** это сделано.

Вызывающий подключает `.h` (`#include "…"`) и пользуется — реализацию видеть ему незачем.

### Пример: три файла

Вынесем работу с точками в отдельный модуль `geometry`.

**`geometry.h`** — что модуль умеет:

```cpp
#pragma once            // защита от повторного включения (см. ниже)
#include <cmath>

struct Point {
  double x = 0;
  double y = 0;
};

double dist(const Point &a, const Point &b);   // ПРОТОТИП: тело — в .cpp
```

**`geometry.cpp`** — как это сделано:

```cpp
#include "geometry.h"   // свой же заголовок — чтобы объявления совпали с телами

double dist(const Point &a, const Point &b) {   // тело функции
  double dx = a.x - b.x;
  double dy = a.y - b.y;
  return std::hypot(dx, dy);
}
```

**`main.cpp`** — пользуется:

<!-- docs:no-compile: часть многофайлового примера (geometry.h показан рядом в тексте) -->
```cpp
#include <iostream>
#include "geometry.h"   // берём объявления Point и dist

int main() {
  Point a{0, 0};
  Point b{3, 4};
  std::cout << dist(a, b) << "\n";   // → 5
  // ...
}
```

`main.cpp` знает про `Point` и `dist` из заголовка, а где их тела — не его забота.

### Защита заголовка: `#pragma once`

Сначала важная деталь про сборку: **каждый `.cpp` компилируется отдельно**, со своим набором `#include`. То, что `geometry.h` подключают и `main.cpp`, и `geometry.cpp`, — не проблема: это две разные «единицы трансляции», и в каждой `Point` определён по одному разу.

Проблема в другом — когда один заголовок попадает **дважды в один и тот же `.cpp`**. Так бывает сплошь и рядом: заголовки подключают друг друга.

```
   main.cpp:  #include "geometry.h"      ← первый раз: Point определён
              #include "route.h"         ← а route.h внутри тоже делает #include "geometry.h"
                                            → второй раз в ТОМ ЖЕ файле: redefinition of 'struct Point'
```

Первая строка заголовка это предотвращает:

```cpp
#pragma once     // «в одном .cpp подставить этот файл только один раз, повторы пропустить»
```

`#pragma once` понимают все современные компиляторы, включая твой g++. Старый способ — «страж включения» на `#ifndef`, его встретишь в чужом коде:

```cpp
#ifndef GEOMETRY_H     // если ещё не определён —
#define GEOMETRY_H     // определяем и включаем содержимое
// ... содержимое заголовка ...
#endif
```

Делают одно и то же; сам пиши `#pragma once` — короче и без выдумывания уникального имени.

### Сборка: все `.cpp` вместе

Собирать нужно **все** `.cpp` разом — заголовки в команду не идут (они подтягиваются через `#include`):

```bash
g++ -std=c++20 -Wall -Wextra main.cpp geometry.cpp -o main.exe
```

> ⚠️ «Run File» в C/C++ Runner (кнопка ▶ или `Ctrl+Alt+R`) собирает **только открытый файл**. Для проекта из нескольких `.cpp` его недостаточно — нужна сборка всех файлов: команда выше руками или [задача сборки в `tasks.json`](#сборка-в-vs-code-все-cpp-папки-одной-кнопкой). Пока задачи однофайловые, это не мешает; всплывает ровно тогда, когда разносишь код.

Забыл добавить `geometry.cpp` в команду — получишь **`undefined reference to dist(...)`**: объявление есть, а тела компоновщик не нашёл. Это [ошибка компоновщика из раздела 27](11-oshibki.md#undefined-reference-to-calcint), и причина у неё ровно эта.

Перечислять файлы руками не обязательно — g++ сам раскрывает шаблон `*.cpp` («все `.cpp` в этой папке»):

```bash
g++ -std=c++20 -Wall -Wextra *.cpp -o main.exe
```

Проверено на твоей сборке: в PowerShell эта команда собирает все три файла примера и программа печатает `5`.

### Сборка в VS Code: все `.cpp` папки одной кнопкой

Чтобы не набирать команду каждый раз, сделай **задачу сборки**. В папке проекта создай `.vscode/tasks.json`:

```json
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "Собрать все .cpp в папке",
      "type": "shell",
      "command": "g++",
      "args": ["-std=c++20", "-Wall", "-Wextra", "-g", "*.cpp", "-o", "app.exe"],
      "options": { "cwd": "${fileDirname}" },
      "group": { "kind": "build", "isDefault": true },
      "problemMatcher": ["$gcc"]
    }
  ]
}
```

Что здесь важно:

- **`"options": { "cwd": "${fileDirname}" }`** — сборка идёт в папке открытого файла, поэтому `*.cpp` находит всех соседей: `main.cpp`, `geometry.cpp` и остальные.
- **`"isDefault": true`** — задача становится сборкой по умолчанию: *Terminal → Run Build Task* (или `Ctrl+Shift+B`) собирает проект.
- **`"problemMatcher": ["$gcc"]`** — ошибки компилятора подсвечиваются прямо в коде и попадают во вкладку *Problems*.
- **`-g`** — отладочная информация, чтобы работал [отладчик](01-osnovy.md#отладчик-увидеть-что-происходит-внутри).

Запуск — в терминале: `.\app.exe`. Один проект — одна папка: если положить в неё `.cpp` от разных задач, в каждом окажется свой `main`, и сборка закончится ошибкой [`multiple definition of 'main'`](11-oshibki.md#multiple-definition-of-main).

### CMake: проект, который собирается одной командой

Когда файлов становится много, а у проекта появляются подпапки и библиотеки, `tasks.json` перестаёт хватать. Стандартный инструмент для этого — **CMake**: ты описываешь проект в файле `CMakeLists.txt`, а CMake сам составляет команды сборки. Unreal Engine использует свою систему сборки, но идея та же — описать проект, а не набирать команды.

Структура:

```
geometry-demo/
├── CMakeLists.txt
└── src/
    ├── main.cpp
    ├── geometry.h
    └── geometry.cpp
```

**`CMakeLists.txt`**:

```cmake
cmake_minimum_required(VERSION 3.20)
project(geometry_demo LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_executable(app src/main.cpp src/geometry.cpp)
target_compile_options(app PRIVATE -Wall -Wextra -Wpedantic -Wshadow -Wconversion)
```

Каждая строка по делу: `project` — имя проекта и язык; `CMAKE_CXX_STANDARD 20` — вместо флага `-std=c++20`; `add_executable(app …)` — «собери программу `app` из этих файлов»; `target_compile_options` — твои строгие флаги.

Сборка — две команды из папки проекта:

```bash
cmake -S . -B build -G Ninja      # один раз: подготовить папку build
cmake --build build               # каждый раз: собрать изменённое
.\build\app.exe                   # → 5
```

```console
$ cmake --build build
[1/3] Building CXX object CMakeFiles/app.dir/src/geometry.cpp.obj
[2/3] Building CXX object CMakeFiles/app.dir/src/main.cpp.obj
[3/3] Linking CXX executable app.exe
```

Первая команда (**конфигурация**) создаёт папку `build` с готовыми правилами; её не нужно хранить в git — она пересоздаётся. Вторая пересобирает **только изменённые** файлы: поправил `geometry.cpp` — `main.cpp` заново не компилируется. На больших проектах это разница между секундами и минутами.

Как поставить (в терминале MSYS2 UCRT64, откуда у тебя g++):

```bash
pacman -S mingw-w64-ucrt-x86_64-cmake mingw-w64-ucrt-x86_64-ninja
```

> **Если в системе несколько компиляторов**, CMake может взять не тот. Явно укажи твой: `cmake -S . -B build -G Ninja -DCMAKE_CXX_COMPILER=D:/msys64/ucrt64/bin/g++.exe`. Имя выбранного компилятора CMake печатает при конфигурации — строка `The CXX compiler identification is GNU 15.2.0`.

В VS Code CMake удобнее через расширение **CMake Tools**: оно само находит `CMakeLists.txt`, а внизу окна появляются кнопки «Build» и «Run». Добавил новый `.cpp` — допиши его в `add_executable` и пересобери.

### Что кладут в `.h`, что в `.cpp`

| В `.h` (заголовок) | В `.cpp` (реализация) |
|---|---|
| прототипы функций | тела функций |
| определения `struct` / `class` | — |
| `const` и `constexpr` | — |
| [шаблоны **целиком**](17-shablony.md) (их нельзя разнести) | — |

Чего в `.h` быть **не должно**:

- **`using namespace std;`** — он расползётся во все файлы, что подключат заголовок ([раздел 24](09-spravka.md#using-namespace-std--почему-в-этом-справочнике-его-нет));
- **тело обычной функции** — если такой заголовок включат два `.cpp`, функция определится дважды → **`multiple definition`**. (Исключение — `inline`-функции и шаблоны: их в заголовок класть можно и нужно.)

### Типовые ошибки

```cpp
// 1. Забыл #pragma once, а заголовок попал в ОДИН .cpp дважды (через другой .h)
//    → redefinition of 'struct Point'. Лечится первой строкой заголовка: #pragma once
//    ⚠️ От multiple definition (пункт 3) #pragma once НЕ спасает — там разные .cpp

// 2. Забыл собрать второй .cpp → undefined reference to 'dist(...)'
//    g++ main.cpp geometry.cpp   ← перечислить ВСЕ .cpp

// 3. Положил тело функции в .h без inline → multiple definition
double square(double x) { return x * x; }          // ❌ в .h так нельзя
inline double square(double x) { return x * x; }   // ✅ либо inline, либо прототип в .h + тело в .cpp
```

> Пока ты решаешь задачи в один файл, это разделение не нужно — не дроби код заранее. Оно появляется естественно, когда файл перестаёт помещаться в голове или функция нужна в двух местах. Что дальше — [раздел 26](09-spravka.md#26-что-учить-дальше).

## Проверь себя

Небольшой разбор по теме. Нажми вариант — сразу увидишь, верно или нет; можно и просто «Показать ответ».

```quiz
В: Что обычно лежит в `.h`, а что в `.cpp`?
+ В `.h` — объявления (заголовки функций, `struct`), в `.cpp` — тела функций
- В `.h` — `main`, в `.cpp` — всё остальное
- Всё равно, куда что класть
= Заголовок подключают многие файлы, поэтому в нём только «обещания». Тело функции должно быть ровно в одном `.cpp`.

В: Зачем в начале заголовка `#pragma once`?
+ Чтобы при повторном `#include` содержимое не вставилось второй раз
- Чтобы файл компилировался быстрее
- Чтобы функции стали `inline`
= Без защиты двойное подключение даёт ошибки повторного определения `struct` и прочего.

В: Тело функции написали прямо в `.h`, заголовок подключили в два `.cpp`. Что скажет сборка?
+ `multiple definition of …` — функция определена дважды
- Всё соберётся
- `undefined reference`
= Каждый `.cpp` получил свою копию тела. Тело — в один `.cpp` (или пометить функцию `inline`).

В: Функцию объявили в `.h`, вызвали, но `.cpp` с её телом не передали компилятору. Что будет?
+ Ошибка компоновщика `undefined reference to …`
- Ошибка компиляции `was not declared`
- Функция вернёт `0`
= Объявление есть — компиляция проходит. А на сборке тела нет. Все `.cpp` передают вместе: `g++ main.cpp math.cpp`.

В: Ты поправил только `geometry.cpp` и запустил `cmake --build build`. Что пересоберётся?
+ Только `geometry.cpp`, потом компоновка
- Все `.cpp` проекта заново
- Ничего — нужно снова запускать `cmake -S . -B build`
= CMake (через Ninja) помнит, какие файлы изменились, и компилирует только их. Конфигурацию `cmake -S . -B build` повторяют лишь при правке `CMakeLists.txt` — да и то CMake обычно делает это сам.
```

Найди ошибку:

```findbug
// geometry.h
struct Point { int x = 0; int y = 0; };
int dist2(Point a, Point b);

// main.cpp и draw.cpp — оба делают #include "geometry.h",
// а main.cpp ещё и подключает draw.h, где тоже есть #include "geometry.h"
// Ошибка: redefinition of 'struct Point'
---
В `main.cpp` заголовок попал **дважды** (напрямую и через `draw.h`), и `struct Point` объявилась два раза.

**Исправление:** первой строкой в `geometry.h` (и в каждом своём заголовке) — `#pragma once`.
```
