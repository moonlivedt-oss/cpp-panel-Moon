## 35. Наследование

> 📖 **Определение.** **Наследование** — когда один класс (**производный**) берёт поля и методы другого (**базового**) и достраивает своё. **Полиморфизм** — вызов одного и того же метода делает разное в зависимости от реального типа объекта. Термины — в [словаре](10-slovar.md#про-классы-ооп).

### Идея: «является частным случаем»

Наследование — способ сказать «тип **B** — это частный случай типа **A**». Круг — это фигура; собака — это животное; кнопка — это виджет. Наследник получает поля и методы базового типа и **добавляет своё**.

```cpp
class Shape {                    // база: общее для всех фигур
 public:
  double perimeter = 0;
};

class Circle : public Shape {    // «Circle — это Shape»
 public:                         // Circle получает perimeter от Shape и добавляет radius
  double radius = 0;
};

Circle c;
c.radius = 2;
c.perimeter = 12;                // поле, унаследованное от Shape
```

`class Circle : public Shape` читается «Circle публично наследует Shape». `public` здесь — это про отношение «является»; оно почти всегда и нужно.

### `protected` — видно наследникам

К `private`-полям базы наследник **не** имеет доступа — они спрятаны даже от него. Если поле должно быть закрыто снаружи, но доступно наследникам, его помечают `protected`:

```cpp
class Shape {
 protected:
  std::string name;      // видно самому Shape и его наследникам, но не снаружи
};

class Circle : public Shape {
 public:
  void setup() { name = "круг"; }   // ✅ наследник видит protected-поле базы
};

Circle c;
c.name = "x";            // ❌ снаружи protected недоступно, как и private
```

### Конструктор наследника вызывает базовый

При создании наследника сначала строится базовая часть. Её конструктор зовут в списке инициализации — первым:

```cpp
class Shape {
 public:
  Shape(std::string n) : name(n) {}
 protected:
  std::string name;
};

class Circle : public Shape {
 public:
  Circle(double r) : Shape("круг"), radius(r) {}   // сначала база Shape, потом своё поле
 private:
  double radius;
};
```

### Виртуальные методы: вызвать нужную версию

Вот ради чего всё затевалось. Пометь метод базы словом `virtual` — и наследник может дать **свою** версию (`override`). Тогда вызов через **указатель или ссылку на базу** попадёт в версию настоящего типа объекта. Это называется **полиморфизм**.

```cpp
class Shape {
 public:
  virtual double area() const { return 0; }   // virtual: наследник может переопределить
};

class Circle : public Shape {
 public:
  Circle(double r) : radius(r) {}
  double area() const override {               // override: своя площадь вместо базовой
    return 3.14159 * radius * radius;
  }
 private:
  double radius = 0;
};

Circle circle(2.0);
Shape &s = circle;             // ссылка на базу, а объект — Circle
std::cout << s.area();         // → 12.5664   вызвалась Circle::area, а не Shape::area
```

Без `virtual` вызвался бы `Shape::area` (по типу ссылки), и полиморфизм бы не работал. Слово **`override`** не обязательно, но пиши его всегда: если сигнатура случайно разойдётся с базовой (`aera` вместо `area`, забытый `const`), компилятор поймает это сразу, а не оставит молчаливый баг.

<details>
<summary>Копнуть глубже: как `virtual` находит нужную версию (vtable)</summary>

Откуда `s.area()` знает, что перед ним на самом деле `Circle`, а не `Shape`? Когда у класса есть хоть один `virtual`-метод, компилятор заводит для этого класса скрытую **таблицу виртуальных функций** (vtable) — список адресов: «`area` вот этого класса лежит тут». А в каждый объект добавляется невидимое поле — **указатель на его таблицу** (vptr), который проставляется в конструкторе: у объекта `Circle` vptr смотрит на vtable класса `Circle`, у `Shape` — на vtable `Shape`. Вызов `s.area()` компилятор превращает не в «прыгни по заранее известному адресу», а в «загляни в vtable этого объекта и прыгни по адресу оттуда». То есть решение, **чью** версию звать, принимается во время работы, по реальному типу объекта, — это и есть **динамическая диспетчеризация**, механизм полиморфизма. Плата невелика: лишнее поле-указатель в объекте плюс один косвенный переход на вызове — потому `virtual` и включают точечно, а не на каждом методе.

Мысленная модель: невиртуальный вызов — как звонок по номеру из блокнота (адрес известен заранее, на этапе компиляции). Виртуальный — как звонок «дежурному этого объекта»: сначала смотришь его личную табличку (vtable), а уже там актуальный номер. Поэтому один и тот же `s.area()` попадает к разным «дежурным» в зависимости от того, чем объект является на самом деле.

</details>

Пустая базовая версия часто бессмысленна («площадь фигуры вообще» — чего?). Тогда метод делают **чисто виртуальным** (`= 0`): база превращается в **абстрактную** — её нельзя создать, только наследовать.

```cpp
class Shape {
 public:
  virtual double area() const = 0;   // чисто виртуальный: у «просто фигуры» площади нет
};
Shape s;                             // ❌ error: нельзя создать абстрактный класс
```

Какая версия `area` вызовется — по шагам. Последний шаг особенно коварный:

```steps
@id c1lk2p9w
# Какой area() вызовется?
Circle circle(2.0);
Shape &s = circle;
double a = s.area();
Shape copy = circle;
double b = copy.area();
---
1 | circle=Circle, радиус=2 | Создали круг. Внутри у него скрытая ссылка на таблицу виртуальных методов **Circle**.
2 | s=→ circle (как Shape&) | Ссылка типа «базовый класс», но смотрит на настоящий `Circle`.
3 | a=12.5664 | `area` виртуальный → версия выбирается по **настоящему** объекту, а не по типу ссылки. Вызвана `Circle::area`.
4 | copy=Shape (срезан) | Копия в переменную типа `Shape` — «срезка»: от круга скопирована только часть `Shape`, радиус потерян.
?5 | b=0 | Чему равно `b`? Теперь объект **действительно** `Shape` → вызывается `Shape::area()`. Полиморфизм работает только через ссылки и указатели.
```

### Виртуальный деструктор — обязателен

Как только у класса есть хоть один `virtual`-метод и его наследуют через указатель на базу, **деструктор базы обязан быть виртуальным**:

```cpp
class Shape {
 public:
  virtual double area() const = 0;
  virtual ~Shape() = default;        // ✅ без этого — беда при удалении через Shape*
};
```

Почему: `delete basePtr` без виртуального деструктора вызовет только `~Shape()`, а `~Circle()` — нет. Ресурсы, которые держал `Circle`, **утекут**, и это [неопределённое поведение](10-slovar.md). С умными указателями ([раздел 33](18-umnye-ukazateli.md)) правило то же: `unique_ptr<Shape>` корректно удалит `Circle` только при виртуальном деструкторе. Правило простое: **есть `virtual`-метод — есть и `virtual`-деструктор.**

### Вызвать базовую версию: `Base::method()`

Переопределяя метод, часто хочется не заменить базовую версию целиком, а **дополнить** её: сделать общую часть базы, а потом добавить своё. Базовую версию зовут по имени класса — `Base::method()`:

```cpp
#include <iostream>

class Enemy {
 public:
  virtual void describe() const {
    std::cout << "враг, hp=" << hp_ << "\n";
  }
  virtual ~Enemy() = default;

 protected:
  int hp_ = 100;
};

class Boss : public Enemy {
 public:
  void describe() const override {
    Enemy::describe();                              // сначала — общая часть базы
    std::cout << "  БОСС, фаза " << phase_ << "\n"; // потом — своё дополнение
  }

 private:
  int phase_ = 1;
};

int main() {
  Boss b;
  b.describe();
  // → враг, hp=100
  //     БОСС, фаза 1
  return 0;
}
```

Без явного `Enemy::` обычный вызов `describe()` внутри метода `Boss` попал бы в **себя же** и зациклился — поэтому базовую версию всегда указывают полным именем. Приём «сначала базовая версия, потом своё дополнение» встречается постоянно: общее поведение живёт в базе и не дублируется, а наследник лишь достраивает частности.

> Родственное ключевое слово — `final`: `void describe() const override final;` запрещает переопределять метод дальше, а `class Boss final : public Enemy` запрещает наследовать сам класс. Ставят, когда хотят зафиксировать конец иерархии.

### Пример целиком: фигуры

Всё вместе — список **разных** фигур через общий базовый тип, и каждая считает свою площадь сама:

```cpp
#include <iostream>
#include <memory>
#include <vector>

class Shape {
 public:
  virtual double area() const = 0;     // у каждой фигуры своя площадь
  virtual ~Shape() = default;          // виртуальный деструктор — обязателен
};

class Circle : public Shape {
 public:
  Circle(double r) : radius(r) {}
  double area() const override { return 3.14159 * radius * radius; }
 private:
  double radius;
};

class Rectangle : public Shape {
 public:
  Rectangle(double w, double h) : width(w), height(h) {}
  double area() const override { return width * height; }
 private:
  double width;
  double height;
};

int main() {
  std::vector<std::unique_ptr<Shape>> shapes;      // разные фигуры в одном списке
  shapes.push_back(std::make_unique<Circle>(2.0));
  shapes.push_back(std::make_unique<Rectangle>(3.0, 4.0));

  for (const auto &shape : shapes)
    std::cout << shape->area() << "\n";   // → 12.5664  и  12  — у каждой своя версия area()
  return 0;
}
```

Один цикл, один вызов `shape->area()` — а выполняется то `Circle::area`, то `Rectangle::area`, смотря что за объект. Добавить новую фигуру — значит просто написать ещё один класс-наследник; цикл трогать не нужно. В этом сила полиморфизма.

### Наследование или композиция

Наследованием часто злоупотребляют. Прежде чем наследовать, проверь отношение:

| Наследование — «**является**» | Композиция — «**содержит**» |
|---|---|
| `Circle` **является** `Shape` | `Car` **содержит** `Engine` (поле, а не база) |
| нужен полиморфизм: разные типы через общий | просто собрать объект из частей |
| `class Circle : public Shape` | `class Car { Engine engine; … };` |

Если тянет написать «A наследует B», но по смыслу A **содержит** B или **использует** B — бери поле (композицию), а не наследование. Наследование оправдано, когда есть настоящее «является» **и** нужен полиморфизм через базовый тип.

### Типовые ошибки

```cpp
// 1. Забыл virtual → вызвалась базовая версия, полиморфизм не работает
class Shape { public: double area() const { return 0; } };        // ❌ не virtual
Shape *s = new Circle(2.0);
s->area();                        // → 0   вызвался Shape::area, не Circle::area

// 2. Забыл virtual-деструктор → утечка при удалении через базовый указатель
class Shape { public: virtual double area() const = 0; };         // ❌ нет ~Shape() virtual
// delete базового указателя не позовёт деструктор наследника

// 3. Срезка (slicing): хранишь наследника в базе ПО ЗНАЧЕНИЮ — «наследная» часть теряется
Circle c(2.0);
Shape base = c;                   // ❌ в base влезла только Shape-часть, radius потерян
                                  //    поэтому полиморфизм — через указатель/ссылку, не по значению
```

> Наследование — мощный, но не первый инструмент. В учебных задачах чаще выручают `struct`, `vector` и свободные функции. Берись за него, когда появляется **семейство типов с общим поведением**, которое надо перебирать единообразно, — и тогда обязательно `virtual`-методы, `override` и `virtual`-деструктор. Что дальше — [раздел 26](09-spravka.md#26-что-учить-дальше) и [cppreference](https://en.cppreference.com/).

## Проверь себя

Небольшой разбор по теме. Нажми вариант — сразу увидишь, верно или нет; можно и просто «Показать ответ».

```quiz
В: Зачем в базовом классе `virtual`?
+ Чтобы через указатель или ссылку на базу вызывался метод настоящего типа объекта
- Чтобы метод нельзя было переопределить
- Чтобы метод стал статическим
= Без `virtual` вызов по `Base &` выберет версию базы, даже если объект — наследник.

В: Что даёт `override` у метода наследника?
+ Компилятор проверит, что метод действительно переопределяет виртуальный метод базы
- Делает метод виртуальным в базе
- Запрещает вызывать метод базы
= Опечатка в имени или `const` — и без `override` получится новый метод, а не переопределение. С `override` — ошибка компиляции.

В: Почему у полиморфной базы деструктор должен быть `virtual`?
+ Иначе при удалении наследника через указатель на базу вызовется только деструктор базы
- Иначе класс нельзя наследовать
- Это ускоряет удаление
= `std::unique_ptr<Base>` на объект `Derived` без виртуального деструктора — ресурсы наследника не освободятся.

В: Как хранить объекты разных наследников в одном векторе?
+ `std::vector<std::unique_ptr<Base>>`
- `std::vector<Base>`
- `std::vector<Derived>`
= В `vector<Base>` наследники «срезаются» до базы. Нужен вектор указателей — лучше умных.
```

Найди ошибку:

```findbug
struct Shape {
    virtual double area() const { return 0; }
};
struct Circle : Shape {
    double r = 1;
    double area() { return 3.14159 * r * r; }   // «переопределили»
};

const Shape &s = Circle{};
std::cout << s.area();       // печатает 0
---
У наследника метод **без `const`** — это другая сигнатура, новый метод, а не переопределение. Через `Shape &` вызывается версия базы.

**Исправление:** `double area() const override { … }` — `override` заставит компилятор проверить совпадение сигнатуры.
```

```challenge
    double r = 0;
    explicit Circle(double radius) : r(radius) {}
    double area() const override { return 3.14159265 * r * r; }
};

struct Rect : Shape {
    double w = 0, h = 0;
    Rect(double width, double height) : w(width), h(height) {}
    double area() const override { return w * h; }
};

int main() {
    std::vector<std::unique_ptr<Shape>> shapes;
    std::string kind;
    while (std::cin >> kind) {
        if (kind == "circle") {
            double r = 0;
            std::cin >> r;
            shapes.push_back(std::make_unique<Circle>(r));
        } else if (kind == "rect") {
            double w = 0, h = 0;
            std::cin >> w >> h;
            shapes.push_back(std::make_unique<Rect>(w, h));
        }
    }
    double total = 0;
    for (const auto &s : shapes) total += s->area();
    std::cout << std::format("{:.2f}", total);
}
```

Карточки на повторение:

```cards
Q: Что делает `virtual` у метода?
A: Включает динамическую диспетчеризацию: вызовется версия из фактического типа объекта, даже через указатель/ссылку на базовый класс. Без `virtual` версия выбирается по типу указателя.

Q: Почему деструктор базового класса должен быть `virtual`?
A: Иначе `delete` по указателю на базовый вызовет только базовый деструктор — производная часть не разрушится (утечка/UB). С `virtual` отработает вся цепочка деструкторов.

Q: Как из переопределённого метода вызвать базовую версию?
A: Через `Base::method()` — например `Base::draw();` внутри `Derived::draw()`. Удобно, когда нужно дополнить поведение базы, а не заменить его целиком.

Q: Наследование или композиция — как выбрать?
A: Наследование — это «является частным случаем» (is-a). Композиция — «содержит/использует» (has-a). Сомневаешься — обычно бери композицию; наследование оправдано при настоящей is-a связи и полиморфизме.

Q: Зачем писать `override`?
A: Это пометка «переопределяю виртуальный метод базы». Если сигнатура не совпала (опечатка, забыт `const`), будет ошибка компиляции, а не тихий новый метод.

Q: Что такое чисто виртуальная функция?
A: `virtual void draw() = 0;` — метод без реализации в базе. Класс с ним абстрактный: создать его объект нельзя, только объекты наследников.

Q: Что такое «срезка» (slicing)?
A: Копирование наследника в объект базового типа по значению: лишние поля отрезаются, виртуальные вызовы идут к базе. Храни через ссылку или указатель.
H: Представь, что `Orc` положили в переменную типа `Enemy`.

Q: Что значит `final` у класса или метода?
A: Класс с `final` нельзя наследовать, метод с `final` нельзя переопределить дальше.

Q: В каком порядке вызываются конструкторы базы и наследника?
A: Сначала базовый, потом наследника. Деструкторы — в обратном порядке.

Q: Чем `protected` отличается от `private`?
A: `protected` члены видны наследникам, `private` — только самому классу.
```

## Закрепление прошлых тем

Три вопроса из тем 13, 18 и 19:

```quiz
В: Тема 13. Как пометить метод, который не меняет объект?
+ `const` после скобок: `int hp() const`
- `const` перед типом: `const int hp()`
- `static int hp()`
= Такой метод можно вызвать у константного объекта и по `const &` — это важно, когда объекты передают по ссылке.

В: Тема 18. `auto a = std::make_unique<Hero>(); auto b = a;` — что будет?
+ Ошибка компиляции: `unique_ptr` нельзя копировать, только перемещать
- `b` и `a` будут указывать на одного героя
- `b` получит копию героя
= Владелец у объекта один. Передать владение — `auto b = std::move(a);`. В этой теме так хранят монстров разных видов.

В: Тема 19. Зачем в заголовке `#pragma once`?
+ Чтобы при повторном `#include` содержимое не вставилось дважды
- Чтобы файл собирался быстрее
- Чтобы заголовок нельзя было подключить из другой папки
= Без защиты два `#include` одного файла дают «повторное определение класса».
```
