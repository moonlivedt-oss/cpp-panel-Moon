## 33. Умные указатели

> 📖 **Определение.** **Умный указатель** — объект, который **владеет** памятью в куче и сам её освобождает, когда выходит из области видимости (это [RAII](10-slovar.md#про-типы-и-память)). Поэтому ручные `new`/`delete` в современном коде не нужны.

### Зачем: беда `new` / `delete`

Как сказано в [разделе 24](09-spravka.md#new--delete--самая-опасная-привычка-из-старых-книг), ручные `new`/`delete` — источник утечек: забыл `delete`, вышел по `return` раньше, бросилось исключение — память утекла. Для массивов ответ известен: `std::vector`, который освобождает всё сам.

Но иногда нужен **один объект в куче** — например, когда его время жизни не совпадает с областью видимости, или (позже, с наследованием) когда тип объекта определяется на ходу. Тогда берут **умный указатель**: он владеет объектом и удаляет его сам, по [RAII](10-slovar.md), — как `vector` со своими элементами.

Вот как выглядит беда ручного `delete` в памяти — и как её убирает `unique_ptr`:

```memory
# Висячий указатель: память освободили, а адрес остался
int* hp = new int(100);
delete hp;
// *hp = 5;  ← неопределённое поведение
auto safe = std::make_unique<int>(100);
// } — конец блока: safe удаляет число сам
---
строка 1
стек main: hp = →#1
куча: #1 int = 100
пояснение: `new` выделил число в **куче** (#1), в стеке — только адрес.
---
строка 2
стек main: hp = →✗
куча: #1 ✗ int = 100
пояснение: `delete` вернул память системе, но `hp` по-прежнему хранит старый адрес — это **висячий указатель**.
---
строка 3
стек main: hp = →✗
куча: #1 ✗ int = 100
пояснение: Запись через `hp` — неопределённое поведение: программа может «работать», пока однажды не упадёт.
---
строка 4
стек main: hp = →✗; safe = →#2
куча: #1 ✗ int = 100; #2 int = 100
пояснение: `make_unique` тоже кладёт число в кучу, но владеет им сам `safe`.
---
строка 5
стек main: hp = →✗
куча: #1 ✗ int = 100; #2 ✗ int = 100
пояснение: `safe` вышел из области видимости и **сам** удалил #2. Ни утечки, ни висячего указателя в живом коде.
```

### `std::unique_ptr` — единоличный владелец

`std::unique_ptr<T>` владеет объектом **единолично** и удаляет его, когда сам выходит из области видимости. Создают через `std::make_unique`:

```cpp
#include <iostream>
#include <memory>
#include <string>

struct Node {
  std::string name;
  int value = 0;
};

int main() {
  std::unique_ptr<Node> p = std::make_unique<Node>();   // Node создан в куче
  p->name = "узел";                                     // -> как у обычного указателя
  p->value = 42;

  std::cout << p->name << " = " << p->value << "\n";    // → узел = 42
  return 0;                                             // здесь p умирает и сам удаляет Node
}
```

Пользуются им как обычным указателем: `p->поле`, `p->метод()`, `*p` — значение. Разница в том, что `delete` писать не нужно **никогда**: объект удалится ровно тогда, когда `p` перестанет существовать, — при обычном выходе, при `return`, при исключении.

«Единоличный» — значит `unique_ptr` **нельзя скопировать** (как работает передача владения — в [семантике перемещения](23-peremeshchenie.md#только-перенос-unique_ptr-и-потоки)) (два владельца одного объекта — это как раз дорога к двойному `delete`). Владение можно только **передать** через `std::move`:

```cpp
std::unique_ptr<Node> a = std::make_unique<Node>();
std::unique_ptr<Node> b = a;              // ❌ error: копировать нельзя — владелец один
std::unique_ptr<Node> c = std::move(a);   // ✅ владение передано c; a теперь пустой (nullptr)
```

Вот как владение «переезжает» при `std::move` — следите, у кого сейчас объект:

```steps
@id c1pddr85
# unique_ptr: владелец всегда один
{
    auto a = std::make_unique<Node>();
    a->value = 7;
    auto c = std::move(a);
    if (!a)
        std::cout << "a пуст\n";
    std::cout << c->value << "\n";
}
---
2 | Node в куче=value 0, a=→ Node | `make_unique` создал `Node` в куче, `a` — его владелец.
3 | Node в куче=value 7 | Через `a->` меняем поле объекта.
4 | a=nullptr, c=→ Node | `std::move(a)` **передаёт** владение: теперь объектом владеет `c`, а `a` пуст. Сам `Node` никуда не двигался!
5 | | `!a` — истина: в `a` ничего нет.
6 | | Печатаем. | a пуст\n
7 | | `c` владеет тем же самым объектом. | 7\n
8 | c=—, a=—, Node в куче=— | Конец блока: `c` умирает и **сам** удаляет `Node`. `a` пуст — ему удалять нечего. Двойного `delete` нет, утечки нет.
```

### `std::shared_ptr` — общее владение

Иногда у объекта честно **несколько** владельцев, и заранее неизвестно, кто освободит его последним. Тогда `std::shared_ptr<T>`: он считает владельцев и удаляет объект, когда исчезнет **последний**.

```cpp
std::shared_ptr<Node> a = std::make_shared<Node>();
std::shared_ptr<Node> b = a;         // копия разрешена: теперь Node владеют оба
std::cout << a.use_count() << "\n";  // → 2   сколько сейчас владельцев

// Node удалится только когда И a, И b исчезнут — за счётчиком следит сам shared_ptr
```

Копировать `shared_ptr` можно — каждая копия увеличивает счётчик, каждое уничтожение уменьшает. Это удобно, но не бесплатно: счётчик надо поддерживать.

<details>
<summary>Копнуть глубже: где живёт счётчик ссылок</summary>

Сам `shared_ptr` — это два указателя: один на объект, другой на **управляющий блок** (control block) — маленький кусочек в куче, где лежит счётчик владельцев (и отдельно счётчик `weak_ptr`). Все копии одного `shared_ptr` смотрят на **один и тот же** блок — потому и видят общий счётчик. Копирование делает `+1`, разрушение — `−1`, причём **атомарно** (потокобезопасно) — вот эта синхронизация и есть та «не бесплатность». Когда счётчик владельцев падает до нуля — удаляется объект; когда обнуляется и счётчик weak — освобождается сам блок. А `std::make_shared<T>(...)` выделяет объект и управляющий блок **одним куском** памяти вместо двух отдельных — поэтому его предпочитают прямому `std::shared_ptr<T>(new T(...))`.

</details>

### `std::weak_ptr` — наблюдать, не владея

`std::weak_ptr<T>` смотрит на объект, которым владеет `shared_ptr`, но **сам владельцем не считается** — счётчик не увеличивает и продлевать жизнь объекта не мешает. Чтобы им воспользоваться, его на время превращают в `shared_ptr` через `lock()`:

```cpp
#include <iostream>
#include <memory>

int main() {
  std::shared_ptr<int> owner = std::make_shared<int>(42);
  std::weak_ptr<int> observer = owner;         // наблюдает, НЕ владеет

  std::cout << owner.use_count() << "\n";      // → 1   weak в счётчик не входит

  if (auto p = observer.lock())                // lock(): взять shared, пока объект жив
    std::cout << "жив: " << *p << "\n";        // → жив: 42

  owner.reset();                               // владелец исчез → объект удалён
  std::cout << observer.expired() << "\n";     // → 1   observer знает, что объекта больше нет
  return 0;
}
```

Главное применение — **разорвать цикл владения**. Если родитель держит детей через `shared_ptr`, а каждый ребёнок ссылается на родителя тоже `shared_ptr`, счётчики никогда не дойдут до нуля и оба объекта утекут. Ссылку «наверх» (ребёнок → родитель) делают `weak_ptr` — цикла нет, и всё удаляется.

### `unique_ptr` или `shared_ptr` — что брать

| `std::unique_ptr` | `std::shared_ptr` |
|---|---|
| владелец **один** | владельцев **несколько**, и порядок их гибели неизвестен |
| дешевле, проще, понятнее | дороже: считает ссылки |
| **выбор по умолчанию** | только когда владение и правда общее |

Правило: **начинай с `unique_ptr`.** `shared_ptr` доставай, когда доказал, что объектом действительно совместно владеют несколько мест. «Общее владение на всякий случай» — частый способ усложнить код без причины.

### Когда они вообще нужны

Честно: в учебных задачах — **редко**. Почти всё закрывают значения и контейнеры:

- список чего-нибудь — `std::vector`, не `unique_ptr` на массив;
- текст — `std::string`;
- «объект или ничего» — `std::optional` ([раздел 9](04-funkcii.md#stdoptional--когда-ответа-может-не-быть)), а не указатель, который может быть `nullptr`.

Умные указатели нужны, когда объект **обязан** жить в куче: узлы связного списка или дерева, объект, чьё время жизни переживает функцию, и (когда дойдёшь до наследования) хранение объекта через указатель на базовый тип. До этих случаев `new`/`delete` не нужны вовсе — и умные указатели тоже.

### Типовые ошибки

```cpp
// 1. Смешивать new с умным указателем — обходить make_unique
std::unique_ptr<Node> p(new Node());     // ⚠️ работает, но пиши make_unique:
std::unique_ptr<Node> q = std::make_unique<Node>();   // ✅ короче и безопаснее

// 2. Тянуться к shared_ptr там, где хватает unique_ptr
std::shared_ptr<Node> s = std::make_shared<Node>();   // ⚠️ если владелец один — это лишний счётчик

// 3. Городить умный указатель на то, что и так значение
std::unique_ptr<int> n = std::make_unique<int>(5);    // ❌ зачем? int n = 5; проще и быстрее
std::unique_ptr<std::vector<int>> v;                  // ❌ vector и так владеет своей памятью
```

> Умные указатели — про **владение** объектом в куче, и это последняя ступень перед «настоящим» C++ (наследование, свои структуры данных). Здесь фундамент: `make_unique` для единственного владельца, `make_shared` для общего, `delete` — никогда. Пока хватает `vector`/`string`/`optional` — они и есть правильный ответ. Карточки на повторение:

```cards
Q: `unique_ptr` или `shared_ptr` — что брать по умолчанию?
A: `unique_ptr` — единоличный владелец, практически без накладных расходов; это выбор по умолчанию. `shared_ptr` — только когда владельцев действительно несколько.

Q: За что отвечает `std::unique_ptr`?
A: За единоличное владение объектом: копировать нельзя, только перемещать (`std::move`). Уничтожает объект автоматически при выходе из области видимости.

Q: Что считает `std::shared_ptr` и когда объект удаляется?
A: Счётчик ссылок в управляющем блоке: копия увеличивает его, разрушение — уменьшает. Объект удаляется, когда счётчик дошёл до нуля.

Q: Зачем нужен `std::weak_ptr`?
A: Наблюдать за объектом, не владея им и не мешая удалению (счётчик не меняет). Разрывает циклические ссылки двух `shared_ptr`; перед доступом вызывают `.lock()`.

Q: Как правильно создать `std::unique_ptr`?
A: `auto p = std::make_unique<Enemy>(аргументы);` — без явного `new`.

Q: Можно ли скопировать `std::unique_ptr`?
A: Нет, только перенести: `auto q = std::move(p);` После этого `p` пустой (`nullptr`).

Q: Как передать объект из `unique_ptr` в функцию, которая только смотрит?
A: По ссылке: `void show(const Enemy &e)` и вызов `show(*p)`. Владение при этом не передаётся.
H: Функции не нужно знать, как объект хранится.

Q: Что случится при циклической ссылке двух `shared_ptr`?
A: Счётчики никогда не упадут до нуля — утечка памяти. Одну из связей делают `std::weak_ptr`.

Q: Как хранить разных врагов-наследников в одном векторе?
A: `std::vector<std::unique_ptr<Enemy>>` и `v.push_back(std::make_unique<Orc>());` — виртуальные методы сработают для каждого.

Q: Как проверить, жив ли объект за `weak_ptr`, и получить его?
A: `if (auto sp = w.lock()) { ... }` — `lock` вернёт `shared_ptr` или пустой указатель, если объект уже удалён.
```

## Закрепление прошлых тем

Три вопроса из тем 13, 22 и 23:

```quiz
В: Тема 22. `int *p = nullptr; *p = 5;` — что будет?
+ Неопределённое поведение, обычно падение программы
- `p` начнёт указывать на `5`
- Ошибка компиляции
= Разыменовывать нулевой указатель нельзя. Перед `*p` проверяй `if (p)` — у умных указателей так же.

В: Тема 23. После `std::string b = std::move(a);` что можно делать с `a`?
+ Присвоить новое значение или дать ему уничтожиться — содержимое не определено
- Читать: в `a` гарантированно осталась старая строка
- Ничего: обращение к `a` — ошибка компиляции
= Из `a` «забрали» содержимое. Объект жив и корректен, но что в нём — не обещано. С `unique_ptr` проще: после `std::move` он точно пуст.

В: Тема 13. Когда вызывается деструктор локального объекта?
+ Автоматически при выходе из блока `{ }`, где объект создан
- Только при вызове `delete`
- В конце программы
= На этом и держатся умные указатели: `unique_ptr` в своём деструкторе освобождает память сам.
```
